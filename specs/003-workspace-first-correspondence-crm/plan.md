### Minimal logical data model and invariants

Names are implementation candidates, not new OS kernel types. Reuse existing org identity and existing application authorization; no independent organization or CRM identity registry. Each key, FK or lookup must include the verified organization scope. Source/mailbox identifiers are stable, not email text as authority. Proposed bounded tables:
- mailbox_source: organization + mailbox ID, provider reference, permitted scope, status (no raw credential).
- message_observation: org/mailbox, scoped Message-ID digest and source identity, message timestamp, direction, necessary normalized metadata only if admitted; historical excluded identities retain minimal digest/state; content and attachments not retained by default.
- source_checkpoint: scoped folder/UIDVALIDITY/UID or adapter cursor, last attempt/success, coverage and error class; checkpoint only after durable processing, re-observe on invalidation; unknown remains explicit.
- registration: organization + stable register number, observed identity or explicit historical group association, date/subject/direction/counterparty, attribution; unique scoped number and unique admitted source association; append-only number semantics and audited correction/withdrawal.
- classification_event / link_event: append-only evidence-based proposals, reviews, classification decisions and scoped exact CRM/project references; no automatic authority. Existing CRM CONTACT-/INT-/PARTY-/OPP-/PRJ- model remains authoritative, validate through admitted provider. No second editable party/project/contacts registry; do not duplicate current CRM interaction history. Link references may be unresolved or stale and require review. A future contract decides whether the correspondence reference becomes an existing CRM interaction record; no independent canonical interaction creation.
- A transactional counter or equivalent serializable lock per organization/register allocates numbers only on committed admission, no reuse or silent renumber. Unique scoped identity, conflict detection, transaction includes audit, same-message retry idempotent; historical equal-requisite group links preserved as such. Excluded historic messages do not re-enter by replay.
- Source observation, classification, admission and read projection are separate capabilities. One ingestion writer per mailbox; no scanner duplicated across Company watcher/WSF roadmap collector/CRM. Read-only Mission Control/Excel via existing BFF release and scoped provider, not direct browser DB access.

### Isolation, recovery and cutover gates

Dedicated NOLOGIN owner, bounded migration role, separate collector/write and projection/read roles, explicit database CONNECT/schema/table permissions, revoke inappropriate PUBLIC privileges in the new database only; verify existing databases/users unaffected. No grant to Data Platform/Tender Agent or external organization by implication. Enforce organization predicates and composite scoped constraints, defense-in-depth RLS where applicable, non-bypass application roles, negative tests of row/role/backup/search/export boundaries. Connection secrets stored through existing approved private secret mechanism, never URI in Git/logs. No new listener, public port, cluster config change or restart. Exact role DDL reviewed separately. Credentials/read scope not inferred from host access.

Before live provisioning: confirm actual resource and storage footprint, existing service ownership and privilege/backup compatibility; verify correct service target, encrypted backup destination and retention/recovery policy; require backup/restore of the new database itself, scoped restore parity including register numbering, event history, identity and constraints, and tested logical/physical recovery compatibility as appropriate.
