# Spec Kit integration with project roadmaps — proposal

Date 2026-11-20. Draft / pending governance review. Extends AC-401…407 implementation work; does not establish new approved policy, authority, release, budget or OS contracts.

## Source and sovereignty
Upstream github/spec-kit, MIT; installed Specify CLI and existing museum/compliance manifests version 1.2.4. Retain license notices, verify exact distribution/source hashes, dependencies, permissions and offline operation before new initialization; no automatic upgrade or unreviewed extensions. Markdown/JSON artifacts remain portable, not proprietary runtime dependencies. No external transfer of customer materials. Preserve current constitutions, RFC/ADR, Product Contracts, AGENTS and native registers. Current upstream documentation includes Converge; availability in pinned version is not assumed. Equivalent verification loop remains mandatory.

## Required lifecycle
Roadmap milestone → spec with requirements and acceptance criteria → plan → stable task/subtask → execution → evidence → verification against exact specification → source update → read-only Mission Control.
Full SDD for production/client/security; lean for low-risk routine work (existing work item and measurable criterion); incident/research profiles for defects and commercial decisions. No forced implementation for held projects. No duplicating canonical task register. For legacy projects import or reference existing IDs and history unchanged; capture complete independently pinned originals, including nested and unchecked items, before modification. Each leaf has ID, parent milestone/task where applicable, source version, requirement links, criteria, dependency, accountable position if assigned, status, evidence, next step/trigger. Show unknown instead of inventing data. Parent closes only when required descendants verified or approved disposition. Cancellation and supersession retain IDs, reason and authorized decision; successor explicit.

## Gates
G0 capture independent source baseline, original requirements/task set, amendments; absent source blocks coverage claim.
G1 cross-artifact completeness, duplicate/missing IDs, dependency cycles, requirement-task mapping and spec/plan consistency; check authorization.
G2 execute without scope drift; keep remaining/failed/partial tasks visible.
G3 check actual result against each exact criterion with versioned evidence; distinguish implemented/verified, customer acceptance, validation failures and not-run. No closure by checklist mark or Git commit alone.
G4 converge: compare implementation/spec/plan/tasks; add newly discovered linked gaps and repeat relevant checks until resolved or explicitly approved disposition.
G5 update authoritative product/work source, then derived MC view: source revision/freshness, open/verified/blocked/unmapped items, next action and waiting trigger. No missing-source zero or automatic authority. Structural validation never proves truth of evidence, business readiness or legal compliance.
